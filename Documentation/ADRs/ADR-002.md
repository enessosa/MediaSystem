# ADR-002: Architectural Decisions

(See visualization in the UML-Component-Diagram)

## Status

Accepted

## Date

26.07.2026

## Context

The backend needs to communicate with several external APIs and its own database. External APIs might change over
time as development and the addition of new Functions continues. The
architecture should represent these changes without requiring modifications.

## Decision

A layered architecture is used: 

``````
React frontend => REST controller => service layer => 
provider/repository interface => concrete implementation =>
external API or own database 
``````
Provider and repository are modeled as interfaces the service layer depends on, rather than classes.
Concrete implementations are shown generically in the architecture diagram
with multiplicity `[1..*]`, without naming individual providers.

## Alternatives Considered

- **Option A:** Service layer accesses concrete provider classes directly.
  rejected because any change/extension of external APIs would then affect
  the service layer.
- **Option B:** List providers by name in the architecture diagram
  (AniList/TMDB/OpenLibrary/...). rejected because the diagram would need to be
  updated every time the provider list changes, even though the architecture
  itself stays the same.

## Consequences

**Positive:**

- New or removed providers only affect the implementation level, not the
  architecture or the service layer (dependency inversion principle)
- Better testability: the service layer can be tested with mock
  implementations of `Provider`/`Repository`
- The architecture diagram stays stable regardless of concrete API decisions

**Negative / Trade-offs:**

- An interface plus generic multiplicity is more abstract and requires a bit
  more explanation

# ADR-010: Prebuilt Images via GitHub Container Registry

## Status

Accepted

## Date

24.10.2026

## Context

With the Docker setup from ADR-009, `docker compose up --build` builds the backend and frontend images on the
machine that runs them. For the target deployment, a UGREEN DXP4800 Plus NAS (Intel, `amd64`), this means
cloning the whole source code onto the NAS and running Maven and npm builds there on every update. That needs
time, memory and a copy of the repository on a device that should only run the app. It also means there is no
clear version of what is running: whatever was checked out at build time.

## Decision

A GitHub Actions workflow builds both images and pushes them to the GitHub Container Registry
(`ghcr.io/enessosa/mediasystem-backend` and `ghcr.io/enessosa/mediasystem-frontend`) whenever a version tag
(`v*`, e.g. `v0.2.0`) is pushed. Each image gets the version as its tag and additionally `latest`. Images are
built for `amd64` only, since that is the only platform in use.

A separate `docker-compose.prod.yml` references these images instead of building them. The NAS only needs that
file and a `.env`; updating means `docker compose pull` and `docker compose up -d`. The existing
`docker-compose.yml` keeps building locally for development. API keys and passwords stay out of the images and
are still passed in through `.env`, so the images can be public.

## Alternatives Considered

- **Option A:** Keep building on the NAS (clone repository, `docker compose up --build`): no additional setup,
  but needs the source code and slow builds on the NAS, and no clear versioning.
- **Option B:** Build on the Mac and push to a registry by hand: no workflow needed, but easy to forget, depends
  on my machine, and the Mac's architecture doesn't have to match the NAS.
- **Option C:** Docker Hub instead of GHCR: the most common registry, but needs a separate account and access
  token, while GHCR works with the repository's built-in `GITHUB_TOKEN` and shows the images next to the code.
- **Option D:** Build and push on every push to `main`: always up to date, but the NAS would run unreleased
  intermediate states; version tags make deployments deliberate.

## Consequences

**Positive:**

- The NAS needs neither source code nor build tools; updates take seconds
- Every deployment is a known version, and going back means changing one tag
- Anyone can run MediaSystem with two files, without cloning the repository

**Negative / Trade-offs:**

- One more workflow to maintain, and two compose files that have to be kept in sync
- Images are only built for `amd64`; an ARM device would need a multi-arch build first
- A fix only reaches the NAS after a new version tag is pushed
